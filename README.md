# Заявки на ремонт

Система учёта заявок на ремонт для управляющей компании ЖКХ. Жильцы оставляют заявки,
диспетчер распределяет их по мастерам, мастер берёт в работу и отчитывается о выполнении
либо отказывается с указанием причины. Каждая смена статуса фиксируется в неизменяемой истории.

Ключевая особенность — **вся бизнес-логика и защита реализованы на уровне базы данных**
(PostgreSQL / Supabase): права доступа, переходы статусов и целостность истории работают даже
при обращении к API напрямую, в обход интерфейса. Это подтверждено автоматическими тестами
безопасности, которые запускаются в CI на каждое изменение.

## Возможности

**Диспетчер**
- создаёт, редактирует и удаляет заявки, назначает мастера;
- закрывает выполненные заявки или возвращает их на доработку с комментарием;
- возвращает отклонённые заявки в работу с переназначением на другого мастера;
- видит все заявки и полную историю по каждой.

**Мастер**
- видит только назначенные ему заявки;
- берёт заявку в работу и отмечает выполненной;
- отказывается от заявки с обязательным указанием причины;
- видит историю своих заявок.

## Безопасность — три независимых слоя

Защита построена так, что ошибка в одном слое не раскрывает данные:

| Требование | Реализация | Файл |
|---|---|---|
| Права закрыты в базе | RLS на всех таблицах; анонимный доступ запрещён полностью | `003_rls.sql` |
| Мастер не видит и не меняет чужие заявки | Политика `select`: диспетчер либо `master_id = auth.uid()` | `003_rls.sql` |
| Статус нельзя изменить напрямую | Колонка `status` недоступна на запись (нет гранта); смена — только через RPC `change_request_status`, а правила переходов проверяет триггер | `002_status_machine.sql` |
| Историю нельзя подделать | На `request_history` выдан только `select`; запись выполняет исключительно триггер | `002`, `003` |
| Переходы статусов проверяются сервером | Таблица допустимых переходов + триггер-охранник на `before update` | `002_status_machine.sql` |
| Секреты не попадают во фронтенд | Клиент использует только публичный ключ; `.env` исключён из репозитория | `.env.example` |

## Жизненный цикл заявки

| Из | В | Кто | Условие |
|---|---|---|---|
| — | Новая | диспетчер | при создании |
| Новая | В работе | назначенный мастер | — |
| Новая | Отказ | назначенный мастер | причина обязательна |
| Отказ | Новая | диспетчер | назначается другой мастер |
| В работе | Выполнена | назначенный мастер | — |
| Выполнена | Закрыта | диспетчер | — |
| Выполнена | В работе | диспетчер | комментарий обязателен |

## Технологии

**Frontend:** React, TypeScript, Vite, Ant Design, React Router
**Backend:** Supabase — PostgreSQL, Auth, Row Level Security, RPC, триггеры
**CI:** GitLab CI — автоматические тесты безопасности на PostgreSQL

## Структура

```
supabase/
  migrations/
    001_schema.sql          схема: типы, таблицы, триггер создания профиля
    002_status_machine.sql  переходы статусов: триггеры-охранники и RPC
    003_rls.sql             доступ: гранты на колонки и RLS
  seed.sql                  демо-данные
  tests/attacks.sql         тесты доступа «в обход интерфейса»
src/
  lib/supabase.ts           клиент Supabase
  auth/                     сессия и профиль с ролью
  api/                      запросы к базе и вызов RPC
  lib/requestActions.ts     доступные действия по роли (отражает правила базы)
  pages/                    экраны: вход, список заявок, карточка заявки
```

## Запуск

### База данных (Supabase)

1. Создать проект на [supabase.com](https://supabase.com).
2. Применить миграции из `supabase/migrations/` по порядку (SQL Editor или Supabase CLI).
3. В **Authentication** отключить самостоятельную регистрацию и создать пользователей.
4. Выполнить `supabase/seed.sql` для демо-данных.

### Frontend

```bash
cp .env.example .env   # указать URL и публичный ключ из Project Settings → API
npm install
npm run dev
```

## Тесты безопасности

Набор проверок доступа «в обход интерфейса»: каждая попытка нарушить правила должна завершиться
отказом. Запускаются автоматически в CI (`.gitlab-ci.yml`) на чистом PostgreSQL и локально:

```bash
./supabase/tests/run.sh
```

Проверяется: изоляция данных между мастерами, запрет прямой записи статуса и истории, запрет
недопустимых переходов, невозможность повысить себе роль, недоступность данных без авторизации.
