# Заявки на ремонт — система учёта заявок для УК

Управляющая компания принимает заявки от жильцов: течёт кран, не работает лифт, перегорела
лампа в подъезде. Диспетчер распределяет заявки по мастерам, мастер берёт заявку в работу и
отчитывается о выполнении либо отказывается с указанием причины. Каждая смена статуса попадает
в неизменяемую историю.

Права доступа, переходы статусов и история защищены **на уровне базы данных** (RLS, гранты на
колонки, триггеры), поэтому работают и при обращении к API напрямую, в обход интерфейса.

## Роли

| Роль | Возможности |
|---|---|
| **Диспетчер** | Создаёт, редактирует и удаляет заявки. Назначает мастера. Закрывает выполненные заявки или возвращает их в работу. Видит все заявки. |
| **Мастер** | Видит только свои заявки. Берёт в работу, отмечает выполненными. Может отказаться от заявки, указав причину. |

## Жизненный цикл заявки

| Из | В | Кто делает | Условие |
|---|---|---|---|
| — | Новая | диспетчер | при создании |
| Новая | В работе | назначенный мастер | — |
| Новая | Отказ | назначенный мастер | причина обязательна |
| Отказ | Новая | диспетчер | одновременно назначается **другой** мастер |
| В работе | Выполнена | назначенный мастер | — |
| Выполнена | Закрыта | диспетчер | — |
| Выполнена | В работе | диспетчер | комментарий обязателен (возврат на доработку) |

Любой другой переход база отклоняет.

## Стек

**Backend:** Supabase — PostgreSQL, Auth, Row Level Security. Вся бизнес-логика и защита живут в базе.
**Frontend:** React 19, TypeScript, Vite, Ant Design *(в разработке)*.

## Как устроена защита

Три независимых слоя — ошибка в одном не открывает данные:

| Требование | Как сделано | Где |
|---|---|---|
| Права закрыты в базе | RLS на всех таблицах; `anon` не имеет прав ни на что | `003_rls.sql` |
| Мастер не видит и не меняет чужие заявки | Политика `select`: диспетчер, либо `master_id = auth.uid()` | `003_rls.sql` |
| Переходы статусов проверяет база | Колонку `status` нельзя обновить напрямую (нет гранта). Смена — только через RPC `change_request_status`, правила — в триггере `requests_before_update` | `002_status_machine.sql` |
| Историю нельзя подделать | На `request_history` выдан только `select`; пишет её только триггер | `002`, `003` |
| Регистрация закрыта | Supabase Auth + роль по умолчанию «мастер» (наименьшие права) | `001_schema.sql` |
| Секреты не во фронте | Во фронте только URL и публичный ключ; `.env` — в `.gitignore` | `.gitignore` |

## Модель данных

- **`profiles`** — пользователь системы и его роль; привязан к учётной записи Supabase Auth.
- **`requests`** — заявка: адрес, описание, срочность, назначенный мастер, статус, автор.
- **`request_history`** — журнал смен статуса: из какого статуса в какой, кто, комментарий, когда.

Срочность вынесена в отдельный тип (`enum`), чтобы позже без миграции данных добавить новые уровни.
История пишется только триггером и связана с заявкой каскадом: удаление заявки уносит и её журнал.

## Структура

```
supabase/migrations/
  001_schema.sql          схема: типы, профили, заявки, история, триггер профиля
  002_status_machine.sql  переходы статусов: триггеры-охранники + RPC
  003_rls.sql             доступ: гранты на колонки + RLS
supabase/seed.sql         демо-данные
supabase/tests/           тесты доступа «в обход интерфейса»
```

## Запуск

### База (Supabase)

1. Создать проект на [supabase.com](https://supabase.com).
2. Применить миграции из `supabase/migrations/` по порядку — через SQL Editor
   или CLI: `supabase link --project-ref <ref> && supabase db push`.
3. Authentication → отключить самостоятельную регистрацию, завести пользователей.
4. Выполнить `supabase/seed.sql` — демо-заявки во всех статусах.

### Фронт

```bash
cp .env.example .env   # URL и публичный ключ из Project Settings → API
npm install
npm run dev
```
